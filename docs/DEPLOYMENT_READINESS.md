# Deployment: Vercel + Render + Neon + Gemini + Cloudflare R2

Updated 2026-11-04 (moved from Google Cloud Run to Render). Nothing has been deployed yet.
Verdict: **READY AFTER MANUAL CONFIGURATION** (see §9).

---

## 1. Architecture

```
Browser ──HTTPS──► Vercel (frontend/ : static React build)
                     │  /api/*  rewrite (reverse proxy, same origin)
                     ▼
              Render web service, Singapore (backend/ : Docker, FastAPI, 1 uvicorn process)
                     ├──► Neon PostgreSQL (Singapore, pooler endpoint, asyncpg, ssl=require)
                     ├──► Google Gemini API (server-side key)
                     └──► Cloudflare R2 (private bucket, presigned GET links only)
   Scheduler (optional) ──X-Reminders-Secret──► POST /api/v1/internal/reminders/run
```

**Why `/api` goes through Vercel instead of the browser calling Render directly.**
Authentication uses an in-memory access token, a refresh cookie that is
`HttpOnly; SameSite=Strict; Path=/api/v1/auth`, and a double-submit CSRF cookie that
JavaScript must read. `*.vercel.app` and `*.onrender.com` are different sites (both are on
the Public Suffix List), so called directly the browser would never send the refresh cookie
and could not read the CSRF cookie. The Vercel rewrite keeps one origin, exactly like the
Vite proxy in development. No auth code changes and no CORS preflights.

| File | Purpose |
|---|---|
| `render.yaml` (repo root) | Render Blueprint: Docker web service from `backend/`, Singapore, health check `/health`, all env vars (secrets as `sync: false`, `SECRET_KEY` generated), redeploys only on `backend/**` changes |

## 4. Phase A: Render backend

1. render.com → sign in with GitHub → **New → Blueprint** → select
   `AI-Clinic-Assistant`. Render reads `render.yaml`.
2. Fill in the `sync: false` values (copy from `backend/.env`):

   | Name | Value |
   |---|---|
   | `DATABASE_URL` | Neon pooler URL (`postgresql+asyncpg://…-pooler…/neondb?ssl=require`) |
   | `GEMINI_API_KEY` | Gemini key |
   | `R2_ACCOUNT_ID`, `R2_ENDPOINT_URL`, `R2_BUCKET_NAME` | from local `.env` |
   | `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | R2 token (Object Read & Write, this bucket only) |
   | `CORS_ORIGINS`, `FRONTEND_BASE_URL` | `https://example.invalid` for now; set in Phase C |

   `SECRET_KEY` is generated by Render (new production signing key; it only ends 15-minute
   access tokens, refresh tokens are unaffected). `ENVIRONMENT=production` turns on Secure
   cookies and requires R2.
3. **Apply.** The first Docker build takes a few minutes. Note the URL, e.g.
   `https://clinic-api.onrender.com` (Render adds a suffix if the name is taken).
4. Verify:
   ```powershell
   curl https://<RENDER_HOST>/health                       # {"status":"healthy"}
   curl https://<RENDER_HOST>/api/v1/public/departments/   # your departments
   ```
   Logs: Render dashboard → clinic-api → Logs (JSON lines with `request_id`).

**Email (D125).** Render's free plan blocks outbound SMTP (ports 25, 465 and 587), so
Gmail SMTP cannot work there: every send fails with `OSError`. The blueprint sets
`EMAIL_BACKEND=brevo`, which sends over HTTPS. Set `BREVO_API_KEY` and `EMAIL_FROM` (a sender
verified in Brevo) in Render → Environment; see docs/EMAIL.md. Without them production sends
**no email**: no registration codes, no appointment emails. On a paid instance, SMTP
(`EMAIL_BACKEND=smtp`, `SMTP_*`) works too. Do **not** set `PORT`,
`COOKIE_SECURE`, `TEST_DATABASE_URL`, `CF_API_TOKEN` or `REMINDERS_OIDC_*` (Google-only).

**Plan.** `plan: free` in `render.yaml` is fine for a demo: 512 MB RAM, and the service
sleeps after 15 minutes idle, so the first request afterwards takes about a minute (it may
time out once through the Vercel proxy; retry). For real use change it to `starter` or
higher (always on).

## 5. Phase B: Vercel frontend

1. Edit `frontend/vercel.json`: replace `REPLACE-WITH-RENDER-HOST` with the host from A3
   (host only, e.g. `clinic-api.onrender.com`). Commit and push.
2. vercel.com → **Add New → Project** → import the GitHub repository.
3. Settings:

   | Setting | Value |
   |---|---|
   | Framework preset | Vite |
   | Root directory | `frontend` |
   | Install / build command | `npm ci` / `npm run build` |
   | Output directory | `dist` |
   | Node.js version | 22.x |

4. Environment variables: `VITE_API_BASE_URL=/api/v1` (must stay relative so the rewrite
   is used); optional `VITE_CURRENCY`, `VITE_SUPPORT_PHONE`, `VITE_SUPPORT_EMAIL`.
   `VITE_*` values are public; never put a secret in one. Do not set `VITE_API_PROXY_TARGET`.
   Live updates (D122): also set `VITE_REALTIME_URL=wss://<render-host>/api/v1/ws` (the host
   from A3). Vercel's `/api` rewrite cannot carry a WebSocket, so the socket goes to Render
   directly; it is authenticated by a one-time ticket fetched through the rewrite, so no
   cookie crosses sites. Without this variable the app works, just without live updates.
5. Deploy and note the URL, e.g. `https://<project>.vercel.app`.

Vercel Hobby is for non-commercial use; plan on Pro for a real clinic.

## 6. Phase C: connect and verify

1. Render → clinic-api → Environment: set `CORS_ORIGINS` and `FRONTEND_BASE_URL` to the
   exact Vercel origin (`https://<project>.vercel.app`, no trailing slash). Save (redeploys).
2. Open the Vercel URL, on desktop and phone:
   - Sign in, reload (session restored), sign out, for each role.
   - Direct load of a deep link, e.g. `/doctors/<id>`.
   - Book, reschedule, cancel an appointment.
   - AI assistant answer **streams** word by word.
   - Live updates: signed in as a patient in one browser and reception (or the doctor) in
     another, book and cancel; the other window updates within a second without reloading.
     DevTools → Network → WS: one `wss://<render-host>/api/v1/ws` per tab, status 101.
     (Render's free plan sleeps after 15 minutes without HTTP requests; the socket then
     reconnects when the service wakes.)
   - Upload a ~10–15 MB patient document and download it.
   - DevTools → Network: calls go to `https://<project>.vercel.app/api/v1/...`; cookies are `Secure`.
3. If streaming arrives in one block or large uploads fail at the proxy, the fallback is a
   custom domain on one registrable domain (`app.example.com` → Vercel,
   `api.example.com` → Render). That needs a small cookie-domain change for the CSRF cookie.

## 7. Phase D (optional): appointment reminders and emails

Without a scheduled run no reminders are created (in-app or email), and queued emails wait
for the next event. The scheduler is the GitHub Actions workflow
`.github/workflows/reminders.yml` (free for this public repository): every 15 minutes,
06:00–22:59 Pakistan time, it calls the run endpoint with the shared secret.

1. Render → clinic-api → Environment: copy the generated `REMINDERS_CRON_SECRET`
   (from `render.yaml`; for a service created before it was added, generate one with
   `python -c "import secrets; print(secrets.token_urlsafe(32))"` and add it).
2. GitHub → repository → Settings → Secrets and variables → Actions → add:
   - `REMINDERS_URL` = `https://<RENDER_HOST>/api/v1/internal/reminders/run`
   - `REMINDERS_CRON_SECRET` = the same value as on Render
3. GitHub → Actions → **Reminders** → *Run workflow* once. The log ends with the counts,
   e.g. `{"appointments_checked":…,"reminders_created":…,"emails_sent":…}`.

Reminder **emails** (24 h and 1 h before, to the patient) also need SMTP on Render
(`EMAIL_BACKEND=smtp`, `EMAIL_FROM`, `SMTP_*`, docs/EMAIL.md). Without SMTP only the in-app
reminders are created. GitHub may start scheduled runs a few minutes late; a late run still
sends the reminder that is due. On the free plan each call wakes the service and Neon.

## 8. Security notes

- [x] No secrets in Git or in the frontend bundle; `.env` files ignored
- [x] Secrets only in Render's environment (`sync: false`), not in `render.yaml` or the image
- [x] Secure cookies, R2 required and dev email outbox refused in production
- [x] CORS: explicit origins only (wildcard refused by config)
- [x] Private R2 bucket, short-lived presigned links; container runs as non-root
- [ ] **Decide** AI PHI policy before enabling `AI_PHI_ALLOWED` / AI document upload
- [ ] Rate limiting is in memory per instance (fine with one instance)
- [ ] **Development and production share the same Neon database and R2 bucket.** Before
      real patients, create a separate Neon branch and R2 bucket for production.
